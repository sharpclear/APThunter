## Minimum Deployment Assumptions

For the first scriptable version, keep the workflow small:

1. Git pull/checkout on the remote machine is done manually before deployment.
2. The local script packages and uploads already-built Docker image archives only. Image builds are done manually before packaging.
3. The remote script loads uploaded images, bootstraps the database through the backend image, and starts containers from those images.
4. The remote script does not delete Docker volumes.
5. The remote script uses the remote `.env` file if present, but does not upload secrets.

## Scripted Image Names

No deployment compose override is used. The remote script therefore uses the image names generated by `docker compose -p apthunter`.

The local packaging script may package images built under the local Compose project name or the target `apthunter-*` image names. It retags selected local source images to the remote target names before saving the archive.

| Service | Image |

## Scripts

| Script | Purpose |
| --- | --- |
| `scripts/deploy-local.sh` | Package already-built local images into `apthunter-images-${DEPLOY_TAG}.tar.gz`, write checksum/manifest files, and upload them to the remote VM. By default it chooses the newest per-service image between the local Compose image prefix, target `apthunter-*`, and the current local Compose container image, then retags it as `apthunter-*` for remote Compose. |
| `scripts/deploy-remote.sh` | Load the uploaded image archive on the remote VM, run the image-contained database bootstrap/migration entrypoint, recreate app containers with `--no-build`, and report health-check failures without rollback. |

DEPLOY_TAG=manual-YYYYMMDD-HHMM

Before running `scripts/deploy-local.sh`, manually build and verify the local images that will be packaged. Run `./scripts/deploy-local.sh --dry-run --tag <tag>` first to confirm source-to-target image mapping. If you need to force one source prefix, use `--source-project apthunter`; otherwise the script uses `--source-project auto`.

## Manual Values Provided

Current values to use when writing the first scripts:

```text
REMOTE_HOST=192.168.32.219
REMOTE_PORT=22
REMOTE_UPLOAD_DIR=/home/mlz/APTHunter/releases
SSH_KEY_LOCAL_PATH=password login
DATABASE_MODE=migrate_existing
REMOTE_ENV_FILE_EXISTS=yes
REMOTE_CAN_ACCESS_INTERNET=yes
```

How these values were chosen:

| Variable | How to choose |
| --- | --- |
| `REMOTE_HOST` | The IP address or DNS name you use from this local machine, for example the host part in `ssh mlz@REMOTE_HOST`. |
| `REMOTE_PORT` | SSH port. Use `22` unless the VM changed SSH to another port. |
| `REMOTE_UPLOAD_DIR` | Directory on the remote VM for uploaded image tar files. Recommended minimal value: `/home/mlz/APTHunter/releases` or `/home/mlz/apthunter-releases`. |
| `SSH_KEY_LOCAL_PATH` | Local private key used by `ssh -i`, for example `~/.ssh/id_ed25519`. If you use password login, note `password login` instead. |
| `DATABASE_MODE` | Use `migrate_existing` for the current remote machine, because the stack is already running. Use `first_deploy` only for a new machine or after intentionally removing the MySQL data volume. |
| `REMOTE_ENV_FILE_EXISTS` | On the remote project root, run `test -f .env && echo yes || echo no`. |
| `REMOTE_CAN_ACCESS_INTERNET` | Use `yes` if the remote VM can pull public images such as Redis/MinIO directly. Use `no` if deployment must be fully offline. |

## Open Decisions Before Implementation

1. Do not add a deployment compose override file.
2. Do not include Redis or MinIO in the offline image archive; the remote VM can pull/use those images directly.
3. The remote deployment script should execute existing SQL migration files from the codebase before starting/recreating the app containers. The deployment scripts should not generate migration SQL; migration SQL is written manually during development.
4. If health checks fail, report the failure and exit. Do not automatically roll back, because many failures may be startup timeout rather than a bad release.

## SSH Password Handling

Do not store the remote SSH password in this file or in deployment scripts.

For the first scriptable version, use normal password login and let `ssh`/`scp` prompt interactively when the script runs. If the script needs multiple SSH/SCP calls, use SSH connection multiplexing to reduce repeated password prompts where practical.

For fully non-interactive deployment, switch to SSH key authentication later and set `SSH_KEY_LOCAL_PATH` to the private key path.
